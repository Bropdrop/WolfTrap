# Proposed ownership of release-sensitive paths

**Status: awaiting organization approval.** This proposal assigns responsibilities by role. A repository administrator and an independent security reviewer must identify eligible individual owners with write access, obtain their consent, and review the actual `.github/CODEOWNERS` change in its own PR. The machine preflight supports explicit individual writer assignments. GitHub also supports visible teams with write access. A team assignment requires independent review beyond this preflight. The proposal has no effect on GitHub permissions. [GitHub code ownership requirements](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)

| Pattern on the protected base branch | Accountable review scope |
| --- | --- |
| `/.github/CODEOWNERS`, `/.github/workflows/`, `/action.yml` | Repository security owners review ownership changes, trigger identity, workflow privileges and dependencies. |
| `/.github/*.lock`, `/.github/qualification-requirements.txt`, `/pyproject.toml`, `/scripts/` | Build and supply-chain owners review every change to build inputs, acquisition, packaging or qualification. |
| `/release/verifier/`, `/release/governance/` | Subscriber security and release-governance owners review verifier bootstrap, policy freshness, identity, required evidence and fail-closed decisions. |
| `/release/qualification/`, `/release/records/`, `/release/custody/`, `/release/recover.py` | Release engineering and independent archive owners review independent oracles, provenance, retention, conflicts and restoration. |
| `/src/wolftrap/`, `/tests/` | Security engine owners review the runtime, installed product, public-source guard, authorization boundaries, test expectations and negative controls. |
| `/docs/`, `/SECURITY.md`, `/LICENSE` | Release documentation, disclosure and licensing owners review subscriber instructions, intended scope, trust anchors and commercial usage rights. |

## Adoption by the repository owner

1. Create a branch from the current protected base. Translate each pattern in the table into a line in `.github/CODEOWNERS` containing that pattern and the actual approved GitHub handles. Set a reviewed catch-all ownership rule first, then the path-specific rules. GitHub uses the last matching pattern. Place all designated owners of a given pattern together on that line. Review file moves and new top-level directories for coverage.
2. Require the code-owner check in the branch protection policy. Require dismissal of stale approvals, approval of the latest reviewable push, and application to administrators. Confirm that a matching change requests review from the intended owner in a disposable draft PR after authorized adoption. Check for parse errors with GitHub's CODEOWNERS errors endpoint and validate representative files against the intended table. A syntax-clean ownership file alone cannot establish effective protection. [CODEOWNERS errors API](https://docs.github.com/en/rest/repos/repos#list-codeowners-errors)
3. Confirm that an author cannot approve their own release, that the last pusher cannot supply the required independent approval, and that membership and organization privileges preserve independent control. GitHub can satisfy a code-owner review with one eligible owner of the file. Where two roles must independently attest, use separate protected release and publication decisions and verify actual distinct identities.
4. Retain the reviewed policy commit and tree, effective branch settings, owner-eligibility evidence, review records and any remaining bypass capabilities in the organization's controlled audit store. Rotate responsibilities on role changes and recheck after ruleset, environment or organization changes. If genuine independent reviewers are unavailable, production remains **BLOCKED**.
