# GitHub governance preflight

Run the read-only collector from an independently reviewed checkout on Ubuntu with Python and the GitHub CLI installed at `/usr/bin/gh`. Authenticate `gh` to github.com with an account authorized to inspect this repository. The ordinary WolfTrap scanner and the standalone subscriber do not use GitHub. No gate in this preflight grants signing, publication or installation authority.

Obtain the expected PR number, full reviewed commit and Git tree from an independent review record. To reproduce the observation for the historical Release Trust draft, run this command from the repository root.

```sh
python -I release/governance/preflight.py --pr 25 \
  --expected-head e652e62377fe9fc096cc3695d9ad49b753ef9941 \
  --expected-tree 6af529bffb4f8610e238f17a8670abce839c9401
```

The command prints `awooo.github-governance/v1` JSON. Each control includes its observable basis. `VERIFIED` means the narrow check passed, `FAILED` means the returned evidence contradicts the required state, and `UNKNOWN` means the available evidence cannot establish the state. HTTP codes and response completeness are recorded per endpoint. A 403 documents inaccessible detail. An absent endpoint may produce 404 for either missing data or insufficient access. A complete empty list is stronger evidence of absence. The separate `caller_has_repository_admin_role` observation describes the signed-in account's repository role. A credential for that account can still lack endpoint permissions.

Exit 1 is `BLOCKED` and exit 2 indicates invalid arguments. Exit 0 is reserved for a fully verified governance profile. This version has no independently qualified adapter identifying every effective publication grant and direct publication bypass, so `publication_permissions` remains `UNKNOWN`. Missing material keeps production blocked even when other settings verify. The [release assessment](governed-release.md) reads the live collector directly.

## Setup by an authorized repository administrator

1. Establish genuine independent security reviewers with repository access, ownership consent, and separate release and publication responsibilities. Adopt a reviewed `.github/CODEOWNERS` on the protected base. The supported profile accepts a single initial `*` rule followed by optional, nonrepeated path patterns in the [ownership proposal](proposed-codeowners.md). Each owner must be a named human with visible current write access. Team membership, alternate file locations, complex pattern overrides and unrecognized syntax need independent validation.
2. In **Settings → Branches**, protect `main` with a classic rule, require at least one approval, require code-owner review, dismiss stale reviews, require approval of the latest reviewable push, apply the rule to administrators and clear bypass allowances for users, teams and apps. Disable force pushes and deletion. Preserve any existing organization policies. This collector reports additional or inaccessible rulesets as `UNKNOWN` until their applicability, interaction and bypass behavior have been independently modeled. Do not remove an existing protection to satisfy this profile.
3. Enable strict required status checks, with GitHub Actions (App ID `15368`) as source. Independently review main-target qualification workflow changes before selecting the six contexts below. The stacked draft workflow filters currently target feature branches. Until the correct runs exist on a PR to main, the release gate cannot pass. Disambiguate check runs by workflow path, run attempt and job/check ID. Avoid duplicate job names on any matching workflow.
4. In **Settings → Environments**, configure `awooo-release-review` and `awooo-publication-review`. Each needs a nonempty, disjoint set of authorized human writers, required review, prevention of self-review and administrator bypass disabled. Select **Selected branches and tags** and allow only the branch `main`. Leave both environments free of stored reusable signing credentials. This profile requires zero environment secrets. Custom protection apps may impose additional restrictions. Actual approvals covering an exact release and deployment remain separate evidence.
5. In **Settings → Actions → General**, default workflow tokens to read-only and disable workflow creation/approval of PRs with that token. Inventory and separately review privileged jobs, installed apps, deployment keys, PATs, roles and external credentials. In the repository release settings, require immutable releases when available. Examine publisher access and negative tests for direct publication paths with the responsible administrator. The release immutability flag alone does not identify authorized publishers.
6. Grant a read-only audit credential the permissions necessary for these GET endpoints through the organization's normal approval process. Relevant fine-grained categories include Metadata, Contents, Pull requests, Checks, Actions, Administration, Environments and environment-secret metadata as required by the endpoints. Do not give production signing authority to the audit credential. Where permissions or settings cannot be verified, retain the HTTP result and leave production blocked. [GitHub REST permissions reference](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens)

## Evidence boundaries

The collector fixes HTTPS host, HTTP method and repository ID in reviewed code. It reads the account, repository, main branch and classic protection, effective branch rules, inherited rulesets, PR and reviews, Git commit, collaborators, exact-head check runs, named workflow PR runs and jobs, CODEOWNERS and errors, Actions permissions, release immutability, environments, deployment branch policy and environment-secret counts. It reads the public main tip and PR again before returning. It accepts no review file, status export, arbitrary URL or alternate host. A public report contains neither review text, credential material, raw response bodies, account names nor secret names. The trusted local OS, `gh`, its configuration, TLS trust store and the authenticated GitHub service are prerequisites.

Each GET has a 12-second timeout, 2 MiB maximum response and a 100-record limit for collections. The collector stops starting requests after 90 seconds. Pagination, unexpected shapes, non-200 statuses, credential failure, rate limiting or unsupported semantics cannot create a successful check. The service has no transaction spanning all GETs. Settings, roles or approvals may change between observations or after collection. A stored JSON report supplies neither authenticated provenance nor fresh authorization.

An approval must be a submitted decisive review of the exact SHA by a distinct human with present write access. A later dismissal or request for changes supersedes earlier approval. A comment does not cancel a decisive review. The latest-push protection requirement is checked separately. The source gate requires the merged PR's reviewed head, the authorized commit and the current main tip all to be identical, with the same Git tree. A squash, rebase or ordinary merge introducing a different main SHA requires a separately authenticated review binding for that exact SHA, which this profile cannot verify. Re-run on the candidate against its actual base rather than treating a draft PR as merged.

The collector verifies the successful GitHub Actions job and check-run IDs, current attempt, path, exact head, repository and target main. These API records cannot by themselves prove the contents of an executed workflow, dependencies or a builder attestation. Preserve independently reviewed source, signing and main-commit authorization records. GitHub account IDs and distinct repository roles also cannot establish distinct people or rule out a compromised administrator. [Branch protection API](https://docs.github.com/en/rest/branches/branch-protection) · [Rulesets API](https://docs.github.com/en/rest/repos/rules) · [Deployments and environments](https://docs.github.com/en/rest/deployments/environments)

Run the offline synthetic contract tests with `python -m unittest -v tests.test_governance_preflight`. They exercise legitimate state transitions, unavailable data, false approvals, bypass configuration, ambiguous check origins, stale source and excessive input. Their fixtures cannot enter the production preflight.
