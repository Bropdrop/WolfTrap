# WT-CRYPTO-005 reconciliation protocol

The effect is one SQLite counter append at the gate. The authoritative gate journal contains an ordered ticket for every increment. A signed archive of finalized tickets permits reconstruction. Rebuilding copies previously committed rows and never calls the execution path.

| From | Operation and evidence | Durable result |
| --- | --- | --- |
| Idle | The anchor verifies the exact operation, nonce, current policy, separate permit and all required signatures. | RESERVED records a random reservation token, policy epoch, expiry, gate generation, prior journal digest, request ID, request digest and evidence digest. |
| RESERVED | The gate signs a domain-separated ARM request with its current incarnation key. The anchor rechecks the exact binding and current policy. | ARMED persists before a signed arm reply is issued. Only one ARM can succeed. The gate accepts that reply only in its live authenticated RPC exchange. |
| RESERVED | Recovery and witness principals sign the same resolution action, realm, reservation token and current revision. | One compare-and-swap records a permanent NOT_COMMITTED fence and removes the permit. Issuing another permit is explicit. A fresh reservation has a different token even when the request ID is reused. |
| ARMED | The gate stages its journal append under BEGIN IMMEDIATE, samples expiry immediately before commit, commits, then signs its ticket as gate-commit. An observer can recover that proof from an exact durable journal match after restart. | The anchor verifies the current incarnation, exact pending ticket and gate signature, consumes the permit and archives the COMMITTED decision and journal row. A retry reads the decision. |
| ARMED | No durable positive proof. This includes silence, expiry, empty gate storage or an unavailable gate. | UNRESOLVED. The permit remains reserved. Execution redelivery, policy transitions and gate replacement cannot clear it. |
| Terminal | Authenticated exact request lookup. | The archived decision can be read repeatedly. A receipt lookup checks the request and evidence hashes. |
| Idle, gate lost | Two scoped signatures approve a new gate public key against the current revision. The replacement fetches the retained signed view, verifies its pin and installs the entire finalized journal into fresh storage. | Gate generation advances. The former key cannot obtain new commit authority. |
| Anchor cache diverges | Live retainer state, independently pinned retainer signature and two repair approvals over its digest and revision. | Repair copies exactly the retained state. It cannot manufacture a terminal decision or discard an outstanding ARM. |

**Serialization and evidence.** The anchor holds a SQLite write transaction while it verifies the independent retained head and advances it by digest CAS and consecutive revision. The retainer commits before acknowledging. The anchor commits its matching state before signing an ARM, fence or finalization reply. A crash between those writes freezes a divergent cache until authenticated repair. TCP sessions bind peer role, service, operation, payload, server challenge and fresh client nonce with separate HMAC keys. ML-DSA-65 signs durable state, receipts and administrative votes with separate domains. Public verification requires trusted provisioning pins, the retainer snapshot, the anchor decision, the gate receipt for a commit or the scoped dual votes for cancellation. Replacement receipts additionally require a dual-approved key lineage.

**Why the negative decision is sound.** Cancellation and arming compete for the same retained revision. Cancellation can win only before any ARM was durably issued. An in-flight old request must still win its original token's ARM and therefore fails after the fence. After ARM, the system has two indistinguishable histories if the gate disk disappears before finalization. It might have crashed before SQLite commit, or committed and lost its proof. Both retain UNRESOLVED. This limitation also applies to pre-SEVERANCE ambiguous reservations without an authenticated phase record. There is no retrospective release or live migration.

**Trust and operating limits.** The retainer is the final rollback trust domain. Its state and signing key, the pinned roots, nonregressing clocks and correct service code must survive the assumed faults. A trusted gate signs only after commit or after observing an exact retained predecessor plus the pending ticket. The offline verifier relies on these signer semantics. Coordinated restoration of gate and anchor is detected while the retainer survives. Loss or rollback of the retainer together with both services is outside the qualification. This small, serial protocol supports one pending reservation at a time. Retained snapshots must fit the inherited bounded RPC frame. An unresolved ARM trades availability for safety.
